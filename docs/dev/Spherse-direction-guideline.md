# Spherse Extended — Guideline of Direction

> **用途**：作为后续需求判断、架构归属和排期取舍的共同准则。它描述长期方向与决策方法，不替代 `backlog.md`、正式 design doc 或版本计划。
>
> **整理日期**：2026-10-25  
> **依据**：Spherse Extended README 与当前已实现功能、`investigationv1-merged` 调研/拟定排期、`guideline-of-direction-draft`，以及关于 Workspace、上下文工程、Subagent/Workflow、插件和 Plan then Build 的后续讨论。

## 0. 一页结论

Spherse 应继续发展为一个**本地优先、可组合、可运行、可分发的个人 Agent 工作空间与创作环境**。核心不是替用户预先做完所有应用，而是让用户能用 Agent、数据、工具、自动化与交互界面，构建过去难以在 Spherse 上实现的个人应用。

方向判断可以浓缩为六条：

1. **先做原语，再做方案。** 优先补齐通用、稳定、可组合的底层能力；具体领域功能优先落在 Workspace、Preset、Skill 或模板中。
2. **把“可运行的应用”作为差异化。** 不止让 Agent 回答或生成 HTML，还要让用户能创建、预览、验证、运行、修改和分发完整 Workspace。
3. **把 Agent 协作从“互相聊天”推进到“可管理的任务执行”。** 先建立任务委派、状态、结果、权限、取消、失败恢复和可追踪性；圆桌是更高层的协作模式，不是第一步。
4. **把上下文工程作为通用运行时能力。** 按任务、事件、数据和状态动态组装上下文；世界书的触发式注入是值得吸收的机制，不是酒馆适配的理由。
5. **可靠性、权限和可观测性随能力一起增长。** Agent 越能自动做事，任务追踪、审计、验证、回滚与恢复越重要。
6. **不因调研发现就自动新增功能。** 外部项目是设计参考，不是需求清单；只有命中真实问题、现有方向或明确验证目标时才进入排期。

## 1. 产品定位

### 1.1 核心定位

**Spherse 是面向个人创作者的通用 Agent Runtime 与可组合应用工作空间。** 用户可以把 Agent、Skill、MCP、数据、Trigger、HTML/UI 和工具组合成一个持续运行、可交互、可修改、可分享的 Workspace。

用户优先级：

- **主要用户：创作者。** 他们希望搭建个人工作流、创作工具、互动空间或小型应用，但不想从零编写完整软件。
- **次要用户：应用使用者。** 他们使用他人或自己制作的 Workspace，不一定关心底层 Agent 架构。
- **开发者和高级用户：扩展贡献者。** 需要 SDK、接口和调试能力，但不应成为产品设计唯一或首要的假设用户。

### 1.2 三个方向的关系

旧草稿中的 A/B/C 方向仍可用，但应理解为**基础、差异化和验证场景**，而非三条互相竞争的产品线：

- **A. 本地 AI 工作空间——产品基础。** 用户有自己的项目数据、Agent、工具与自动化，AI 能在受控的工作区内持续工作。
- **C. 个人 AI 应用构建环境——长期差异化。** 用户不只是使用 Agent，也能借助 Agent 组装数据结构、界面、操作和工作流，形成真正可运行的微型应用。
- **B. 创作与世界观工作空间——重要验证场景。** 世界观构建、角色扮演、互动叙事和 TRPG 可以证明基础原语足够灵活，但不应决定 Runtime 的数据模型和产品边界。

推荐的定位表达：**以通用工作空间为底座，以应用构建与组合能力为差异化，以多种真实 Workspace 验证通用性。**

### 1.3 不是什么

- 不是把所有热门 Agent 功能都内置进来的功能集合。
- 不是以 Tavern/角色卡/世界书为中心的专用 Agent。
- 不是要求每个 Agent 都拥有复杂的人类式长期记忆。
- 不是一开始就追求完全自主、自由互联的 Agent 群体。
- 不是先建立大型插件市场，再寻找插件能解决什么问题。

## 2. 架构归属：核心、SDK、Workspace、插件

先判断需求需要哪一层解决，再讨论具体实现。

| 层 | 应负责什么 | 常见例子 | 不宜承担什么 |
|---|---|---|---|
| **Runtime 核心** | 跨应用共用的执行语义与可靠性保证 | Session/Agent 执行、工具调用、上下文装配、事件、权限、任务状态、结构化数据访问、归因、回滚基础 | 角色关系、章节规则、词汇学习算法等领域业务逻辑 |
| **官方 UI 与基础交互** | 高频、普遍、需原生一致体验的通用操作 | 聊天、模型切换、通知、文件标签、基础 Markdown/JSON 查看、Token 状态 | 为每个 Workspace 预设特殊页面和交互 |
| **SDK / 扩展接口** | 为自定义 UI、数据与能力提供稳定的受控入口 | HTML/UI SDK、数据/卡片 API、事件订阅、渲染器注册、受限操作、辅助模型调用接口 | 未经稳定契约暴露内部实现细节 |
| **Workspace / Preset / Skill / 模板** | 领域数据模型、业务规则、特定工作流与应用界面 | 世界观工作台、TRPG、语言学习、个人资料库、阅读器、角色关系图、特定 Agent 的记忆策略 | 重复实现通用权限、任务生命周期和数据一致性机制 |
| **插件** | 独立安装、配置、授权、升级的代码级扩展；在现有机制不足时扩展 Runtime/全局 UI 行为 | 自定义文件查看器/渲染器、特殊 Provider/集成、Plan then Build 行为扩展、全局任务面板 | 把本来可由 Skill、MCP、Workspace 或 HTML 实现的功能一律插件化 |
| **可分发方案 / 社区包** | 将一组已组合好的应用方案交给他人使用 | Workspace Bundle、示例项目、领域预设、插件集合 | 假定接收方拥有相同 API Key、MCP 服务、文件路径或运行权限 |

### 2.1 实用的归属规则

把需求放进 Runtime 核心，至少应满足大多数条件：

- 多种独立 Workspace 都需要它，而不只是相似的单一用例。
- 它决定执行正确性、安全性、数据一致性或跨平台行为。
- 多个上层方案确实需要相同的稳定契约。
- 如果不由 Runtime 保证，各 Workspace 会以不一致或不安全的方式重复实现。

优先放在 Workspace/预设层，当：

- 数据结构、业务规则或排序策略依赖某个领域。
- 现有 `.data.json`、`.card.json`、Skill、Trigger 和 HTML/UI SDK 足以实现。
- 价值来自特定组合方式，而不是新底层机制。

考虑插件，当：

- 需要新增或替换 Runtime 行为、全局界面，或接入当前 SDK 尚未开放的能力。
- 功能需要独立的安装、启用、授权、升级、禁用与版本兼容生命周期。
- 多个 Workspace/用户有复用价值，且单纯复制 Workspace 模板不合适。

**常见需求不自动等于核心能力；某项能力可被插件实现，也不代表必须做成插件。** 对长期稳定、普遍且与安全相关的基础行为，内置往往更合理。

## 3. 长期能力方向

### 3.1 可靠的 Agent 执行与协作

目标不是尽快堆出大量 Agent 或让 Agent 任意互相发消息，而是让多 Agent 工作变成可观察、可管理和可恢复的任务执行。

建议演进顺序：

1. **任务委派 / Subagent：** 主 Agent 发起任务；被委派 Agent 有明确目标、输入引用、权限、输出契约、状态和结果回传。先从层级式编排开始。
2. **可控 Workflow：** 将 Agent、工具、条件判断、审批和脚本组成可复用流程；可串行、可重试、可取消，必要时再支持并行。
3. **多轮协作：** 研究 → 审核 → 修改，或生成 → 校验 → 修复。
4. **Agent 圆桌：** 作为一种更高层的讨论工作流，在有明确参与者、轮次、发言终止条件和结果汇总方式后再实现。

无论哪一步，都应关注任务 ID、Session 关联、输入/输出、状态迁移、超时、成本、权限、错误、取消和恢复。尽量避免让多个 Agent 直接并发修改同一份重要数据；使用结构化提案、受控写入、版本号或冲突检测。

### 3.2 应用创建：从“能生成 UI”到“能交付应用”

这是长期最值得投入的差异化方向之一。理想的创建闭环是：

**描述需求 → 澄清边界 → 生成数据与 UI 结构 → 绑定 SDK/工具/自动化 → 自动验证 → 隔离预览 → 修复问题 → 保存为 Workspace → 继续迭代和分发。**

优先补齐使这个闭环可靠的基础：

- 可复用的应用模板与清晰的数据契约。
- Schema / SDK 调用检查和运行时错误反馈。
- 隔离预览、测试数据或模拟事件，避免初次生成就修改真实数据。
- 可追踪的文件/数据变更、版本快照与恢复入口。
- Workspace 导入导出、依赖声明、版本兼容和迁移提示。

“Agent 生成更多代码”不是最终验收标准。验收标准应是：用户能否创建并持续运行一个实际解决问题的 Workspace，并能理解和修复它的问题。

### 3.3 通用上下文工程

把上下文装配视为 Runtime 的核心能力之一。目标不是复制某个应用的提示词格式，而是按任务与状态，为 Agent 选择适当信息，并能解释这些信息为何进入上下文。

可持续发展的机制包括：

- 会话、Agent、项目与任务状态的上下文组合。
- 关键词、正则、事件、条件和常驻规则等触发式注入方式。
- 可配置注入位置、优先级、作用域、来源与 Token 画像。
- 工具结果截断/引用指针、压缩、历史上下文恢复和按需取回。
- 可观测的上下文预览与调试：实际注入了什么、来自哪里、为什么命中、占用多少预算。

**世界书在此处的意义是触发式上下文注入机制的一个实例。** 它最初参考 SillyTavern 的上下文拼装思路，不应被误解为为了兼容酒馆卡而作的产品决策。角色设定只是应用之一；资料检索、创作规则、当前场景、任务约束也可以采用相同机制。

同时，避免将某种领域元数据固化成 Runtime 的通用排序规则。例如依赖章节距离的叙事排序可以作为 Workspace 的策略；Runtime 提供通用过滤、排序接口和上下文预算能力即可。

### 3.4 记忆：帮助继续工作，而不是模拟人脑

Runtime 的通用记忆目标应先保持克制：帮助 Agent 延续工作、记住稳定偏好/项目假设、取回有用的历史依据，而不是默认实现一套复杂的“人类大脑”。

建议区分：

- **稳定偏好与全局约束：** 少量、经过用户确认的长期信息。
- **项目事实与决策：** 当前 Workspace 的事实、决策、约束及其来源。
- **会话/任务经历：** 过去做了什么、为什么做、下一步是什么。
- **检索索引：** FTS、向量或混合检索等派生索引，可重建，不作为唯一事实来源。
- **应用专属记忆：** 例如关系进度、剧情状态、特定业务的经验，由 Workspace 定义结构、提取和召回策略。

优先级应是：正确性、作用域隔离、来源可追溯、纠错/更新/删除、用户可治理、可靠写入与回滚，然后再是召回覆盖面。不要把所有消息自动灌入长期库，也不要在没有评测的情况下假定复杂记忆架构会比清楚的文件与检索更好。

调研中的 `memory.jsonl`、向量接口与多阶段记忆提案应视为设计候选，而非不可变约束。可以保留“单一事实源、索引可派生、可审核/纠错”的原则，具体存储实现应结合当前上游变更与迁移成本重新评估。

### 3.5 结构化输出与交互卡片

Agent 的输出不应只有普通文本。结构化结果、卡片、报告、任务状态和可执行操作需要稳定的数据契约与渲染边界。

方向包括：

- 统一的输出标记/解析器，区分普通文本、结构化卡片、文件产物、状态与需要用户批准的操作。
- 清晰的 Schema、渲染器和错误处理方式。
- AI 先提出修改建议，再由用户或受控流程批准应用；不要仅凭模型输出的 HTML/脚本就直接执行高风险操作。
- 支持工具、Trigger、Agent 和自定义 HTML 页面复用同样的数据契约。

这类能力既改善聊天体验，也会成为应用构建、自动化和多 Agent 协作的共同基础。

### 3.6 事件与自动化

Trigger 不应只有“到时间就调用 Agent”，而应逐步发展为可调试的自动化系统：事件过滤、去重/idempotency、队列与并发控制、优先级、超时、重试、取消、模拟/预览、运行历史和错误定位。

可区分两类动作：

- **Agent 任务：** 适合需要判断、理解或生成的工作。
- **普通脚本/确定性工具：** 适合结构明确、可重复验证的工作，不应为了调用能力而强制启动 Agent。

建议每次执行有稳定的 `run_id`，关联事件来源、Agent/Session、输入输出、文件变更、耗时、Token/费用和失败原因。自动化越自主，越需要权限、限流、幂等与恢复机制。

### 3.7 文件、查看器与可视化

文件系统和查看器应分层：文件管理负责发现、组织与受控读写；查看器负责把格式呈现出来；编辑器负责特定格式的变更与保存；SDK 提供统一接入方式。

- 对普遍、高频、基础的格式和操作，可以由官方原生支持。
- 对长尾格式、专业格式或社区偏好的表现方式，可以考虑查看器适配器/插件。
- 对单一 Workspace 的时间轴、关系图、世界观地图等，先用 HTML/UI SDK、Skill 或模板验证，不必立即进入 Runtime。
- 只有当查看器需要被跨 Workspace 注册、独立安装/升级，或改变全局文件打开行为时，才需要更正式的扩展机制。

“支持打开某种文件”与“允许用户用任意 HTML 读写所有工作区文件”是不同的问题。尤其是 SDK 写入，必须同时设计路径策略、作用域、权限、大小/数量上限、并发锁、变更归因、版本链与回滚；不要为了快速生成应用而开放过宽的写入面。

### 3.8 安全、信任与可观测性

这是能力增长的前置条件，不应被视为最后的打磨工作。

- **最小权限：** 按资源和动作授权，区分安装扩展、在 Workspace 启用、允许某个 Agent 调用。
- **透明执行：** 能追溯谁发起了操作、哪个 Agent/工具执行、访问了什么、改了什么、结果是什么。
- **有界自主：** 明确批准点、危险操作限制、超时与取消；System Prompt 不能替代运行时强制的权限检查。
- **可恢复：** 对关键数据有版本、事务或可撤销变更记录；清楚说明哪些外部副作用无法回滚。
- **可调试：** 提供统一运行记录，而不是问题发生后只能翻日志或重现整个会话。

这些不是与应用构建无关的“安全功能”；它们决定用户是否敢把真实任务交给 Agent，以及生成的 Workspace 是否能长期使用。

### 3.9 评测与回归

调研识别出的较明确缺口是 Agent/Workspace 评测体系。它值得作为独立的质量基建候选，而不是只在功能完成后人工体验。

建议渐进实现：固定任务集与输入种子、结构化验收标准、可重复的执行环境、评分记录、必要时跨模型评委、baseline 与版本回归。优先覆盖真实高频用例：任务是否完成、产物是否有效、数据是否正确、是否错误召回过期事实、是否越权、失败后是否可恢复。

不必一开始就建立庞大评测平台。先让关键能力可测、结果可比较，再随着用例增长扩展。

### 3.10 Workspace 分发与扩展生态

社区和插件市场是可能的长期方向，但不应先于本地方案的可迁移性。

推荐顺序：

1. 本地 Workspace 导出/导入能稳定工作。
2. 声明插件、Skill、MCP、Provider 和权限等依赖，并检查兼容性。
3. 支持升级、迁移、冲突处理、禁用和恢复。
4. 再考虑社区目录、发现、评价、来源验证和更丰富的插件生态。

分享包不能假设接收方拥有相同 API Key、MCP 服务、模型配置和本地路径；导入前要明确展示缺失依赖、外部访问能力与权限变化。

插件的核心价值不是“再多一种安装形式”，而是在 Skill、MCP、Workflow 和 Workspace 都不足以表达时，为 Runtime 或全局 UI 提供有生命周期的代码级扩展。

## 4. 需求进入排期前的判断流程

每个新想法先回答下列问题。答案不全时，可以先做小型原型或调查，不急于承诺版本。

### A. 问题是否真实

- 来自自己的实际使用痛点、用户反馈，还是只因为调研中看到别人有？
- 目前能否用已有 Agent、Skill、MCP、Trigger、数据文件或 HTML/UI SDK 组合实现？若能，真正的问题是缺少功能，还是缺少模板、文档或更好的创作体验？
- 是否已经出现尴尬绕路、重复实现、用户需要改核心代码的情况？

### B. 应该解决哪一层

- 是跨 Workspace 的执行原语，还是领域业务规则？
- 是普遍的内置交互，还是特定应用的视图？
- 能否用现有 SDK 实现？若不能，缺少的稳定接口到底是什么？
- 插件需要修改 Runtime 行为，还是一个 Workspace 模板就够？

### C. 通用性与杠杆

- 它能服务至少两个独立场景吗？是否存在共同机制，而不是仅仅名字相似？
- 它是否让用户能构建之前无法构建的应用？
- 是否降低其他功能的实现成本，或提升可靠性、可维护性？
- 如果这是领域特有能力，是否把它留在 Workspace，并在出现第二个独立消费方时再考虑抽象？安全、权限和数据一致性机制不必等待第二个用例。

### D. 风险与长期成本

- 是否扩大文件、网络、模型、工具或跨会话的访问面？
- 是否支持权限隔离、运行记录、失败处理和恢复？
- 是否引入新的状态源、依赖或难以迁移的数据格式？
- 是否增加上游合并成本，或与既有架构产生重复机制？

### E. 能否验收

- 成功行为是什么？有什么可观察的验收标准？
- 是否能通过一组真实任务进行验证，并在未来回归测试？
- 最小可行版本是什么？哪些能力明确暂不做？

## 5. 优先级建议

使用“用户价值 × 架构杠杆 × 实现把握度”判断收益，并同时考虑开发成本、风险和长期维护成本。分数只是帮助比较选项，不是市场预测。下列规则用于决定先后，而不是替代具体估算。

### P0：正确性、信任与核心工作流阻塞

典型条件：数据可能丢失或污染；跨 Agent 写入存在不一致；权限边界不清；任务失败无法定位/恢复；已有关键工作流被明显阻塞。

可能涉及：受限写入及回滚归因、任务生命周期与运行记录、关键操作授权、Context/输出边界的可靠性、测试与错误反馈。

### P1：提高组合能力或解锁新工作流

典型条件：同一机制能让多个场景变得可实现，或显著缩短用户从想法到可运行 Workspace 的路径。

可能涉及：应用创建/验证/预览闭环、结构化输出与交互卡片、Subagent 任务契约、可控 Workflow、上下文调试、基础 Agent/Workspace 评测。

### P2：可由 Workspace/预设验证的场景能力

典型条件：价值明确，但现有原语基本覆盖，主要工作是数据 Schema、Skill、HTML/UI 和组合设计。

可能涉及：世界观可视化、TRPG、语言学习、阅读器、时间轴/关系图、特定领域的记忆提取与召回。

### P3：规模化、生态化与长尾扩展

典型条件：核心接口稳定、至少有几个真实扩展需求，且生命周期、权限和兼容策略清楚。

可能涉及：插件目录、社区分发、全局 UI 扩展、复杂的查看器注册生态、广泛的第三方扩展市场。

> 某个项目看起来复杂或先进，并不是提升优先级的理由。一个小而关键的可靠性改进，可能比一个大型新功能更有杠杆。

## 6. 对现有调研排期的使用方式

调研 PDF 明确把版本和新增项标注为**提案，非 design doc，落地前需评审**。因此，排期应当作为待验证假设，而不是已批准承诺。

现有大版本主题可以作为导航：

- `v1.0.0`：Game Engine
- `v1.1.0`：Writing Copilot & Storage
- `v1.2.0`：Tools
- `v1.3.0`：Mobile
- `v1.4.0`：Other Platforms
- 持续保持与上游兼容

建议每次排期时遵循以下做法：

1. **保留版本主题，但允许按依赖重排具体条目。** 版本号不应阻止先补安全、数据一致性或公共接口。
2. **调研结论不自动转成需求。** 对照项目已做的功能，可复用其技术否决和验证结论，但只有命中 Spherse 的问题才进入计划。
3. **优先复用现有原语。** 例如，时间轴/关系图先由通用 Skill + HTML/UI SDK 验证；语言学习先用 Workspace + `.data.json` + Trigger 验证；不要仅为单一用例新增 Runtime capability。
4. **抽象要有证据。** 当第二个独立场景真正需要同一机制，或一开始就涉及跨应用安全/可靠性保证时，再提升为共用接口。
5. **明确状态。** 将项目项区分为：已决定、候选、待调查、实验、已排期、已完成、明确不做，避免提案和承诺混淆。

### 6.1 值得单独审视的候选

以下是从调研与后续讨论中归纳出的候选方向，不等于立即排入某个版本：

- **Agent/Workspace 评测 harness：** 调研指出现状缺少系统化评测；建议先用关键任务与 baseline 建立最小闭环。
- **任务委派与 Workflow：** 在当前 `>> <slug> <消息>` 召唤机制上补齐结构化任务、状态、结果、取消、超时、权限与追踪；圆桌作为更高层用例。
- **应用构建闭环：** 评估需求澄清、Schema/SDK 验证、隔离预览、错误修复、版本与导出能力之间的依赖关系。
- **辅助式模型调用：** 翻译、识图、`/card:{prompt}` 等可能共用“不进入主会话历史、可选专用 Provider、结果渲染到 UI”的旁路调用机制。先验证通用契约，再决定哪些具体入口值得做。
- **受控文件写与恢复：** 不应开放不受限的 SDK 文件写入。先明确窄权限、数据契约、归因/版本链与回滚路径。
- **基础记忆治理：** 优先解决来源、作用域、更新/删除、纠错和会话工作状态延续；向量检索与自动整理按实测收益逐步推进。
- **导入导出与插件/社区：** 本地包、依赖声明、兼容性、权限预览和升级迁移优先于在线市场。
- **文件查看器扩展点：** 通过 PDF/CSV 等常见格式和自定义视图的真实需求，判断原生查看器、Workspace viewer 和插件注册接口之间的边界。
- **Plan then Build：** 可作为验证 Agent 行为扩展能力的试验。先确保任务阶段、工具限制、批准点、计划持久化与执行状态有稳定接口，再考虑将其实现为插件；不能只依赖提示词来强制执行阶段边界。

## 7. 对已有功能的方向性解读

当前新增功能总体符合通用 Agent 工作空间的方向。聊天体验、会话模型配置、Token 展示、上下文压缩、Trigger 事件、回滚、文件与标签管理、HTML 内嵌实时聊天等，都在补齐跨场景基础能力。

世界书也不应简单归类为酒馆专用功能。其条目管理和特定使用约定可能来自角色扮演场景，但触发式注入、条件判断、注入位置、来源和 Token 成本观察等机制本身具有通用价值。应保留它在特定场景的实用形态，同时让底层上下文装配机制保持独立。

相对而言，桌宠模式、专用世界观模板、特定角色卡格式等更接近可选交互或领域方案；它们可以继续存在，但不应反向决定 Runtime 的抽象。

## 8. 设计与交付的最低要求

一个新功能进入正式实现前，设计说明至少应包含：

1. 用户问题和当前绕路方式。
2. 为什么它属于所选层级，以及为什么不应由更低成本的现有机制实现。
3. 最小实现范围与明确不做的部分。
4. 权限、数据范围、失败与恢复行为。
5. 验收标准和回归用例。
6. 与上游、现有 API、旧数据和未来迁移的兼容策略。
7. 交付后的可观察指标：使用是否成功、失败原因、数据正确性、成本或延迟等。

对于高风险写入、自动化和多 Agent 功能，权限、追踪与恢复应是设计的一部分，不能作为之后再补的 UI。

## 10. 最终判断原则

面对新需求时，先不要问“要不要给 Spherse 加这个功能”，而是依次问：

1. 用户究竟想完成什么任务？
2. 当前哪一项通用能力阻止了这个任务？
3. 这个缺口应该由 Runtime、SDK、Workspace 还是扩展机制负责？
4. 怎样用最小实现证明该抽象能被真实场景复用？
5. 如何保证它可追踪、可验证、可恢复，并且不破坏已有 Workspace？

**Spherse 的成功不在于内置功能的数量，而在于它提供的原语能组合出多少有价值、能可靠运行、又能被用户持续修改和分享的应用。**
